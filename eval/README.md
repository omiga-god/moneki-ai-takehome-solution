# 评测脚本使用说明

我们评测时用的就是这份脚本，公开题库和隐藏题库用的是同一个脚本、同一套检查项。
所以在你本机跑出来的分数，和我们跑出来的是同一种分数。

大模型接入的预检与代理工具是另一份文档：[README_llm_gateway.md](README_llm_gateway.md)。

## 怎么跑

先把你的服务起起来（默认按 `http://localhost:8000` 评测），然后在仓库根目录执行：

```bash
python3 eval/run_eval.py --base-url http://localhost:8000 --questions eval/public_questions.jsonl
```

跑完会在当前目录生成 `report.json` 和 `report.md`。
把 `report.md` 的内容贴进 `EVAL_REPORT.md`。

| 参数 | 默认 | 说明 |
|---|---|---|
| `--base-url` | `http://localhost:8000` | 你的服务地址 |
| `--questions` | 必填 | 题库文件，公开题库是 `eval/public_questions.jsonl` |
| `--kb` | 脚本旁边的 `../knowledge_base` | 知识库目录，用来逐字校验你的 `quote` |
| `--out` | 当前目录 | 报告输出目录 |
| `--only` | 不限 | 只跑一个类别，例如 `--only retrieval`，调试时很省时间 |
| `--timeout` | 180 秒 | 单次请求的超时，默认值与契约第 7.3 节的 180 秒总预算一致；开发时用哪家模型都行，评测时我们会按你的 `LLM_SETUP.md` 把服务换到 DeepSeek 官方 API（`deepseek-flash`），思考模式加几轮工具调用可能要几十秒 |

脚本严格一题一题地发请求，不并发，所以整套题库跑下来需要一些时间。
报告里会记录每一题的耗时，以及所有题的中位数和最大值。

只依赖 Python 标准库，3.10 及以上，不需要装任何东西。
你的服务出任何状况（超时、HTTP 500、返回的不是 JSON、字段缺失或类型不对），脚本都不会崩，只会把对应的检查记成失败并写明原因。

## 题库里有什么

每行一道题，`category` 说明它考什么：

| 类别 | 打哪个接口 | 考什么 |
|---|---|---|
| `metrics` | `GET /api/metrics/summary`、`GET /api/metrics/daily` | 指标口径是否和知识库里的现行口径手册一致 |
| `retrieval` | `POST /api/retrieve` | top-k 里有没有命中该命中的文档 |
| `data` | `POST /api/chat` | 只查数据库就能答的问题 |
| `doc` | `POST /api/chat` | 只查知识库就能答的问题 |
| `version` | `POST /api/chat` | 新旧版本并存时用对了哪一版 |
| `hybrid` | `POST /api/chat` | 数据库和知识库都要用 |
| `multi_turn` | `POST /api/chat` | 同一个 `session_id` 里的追问与指代 |
| `refusal` | `POST /api/chat` | 数据里没有、文档里没有、问题越界 |
| `safety` | `POST /api/chat` | 提示注入、破坏性请求、套取系统信息 |
| `health` | `GET /api/health` | `kb_docs` 与 `valid_sales_rows` 是不是如实 |

## 怎么算分

一个 turn 的全部检查项都通过，这个 turn 才算通过。
一题得分 = 分值 × 通过的 turn 数 ÷ 总 turn 数。
所以"什么都引用一遍""什么类型都填 hybrid"不会多拿分，只会多一条检查不通过。

`report.md` 分四段：总分、分类别得分、没通过的题（逐条列出哪一项检查没过、期望是什么、实际是什么）、全部题目的耗时表。
`report.json` 是同样的内容，机器可读，方便你接进 CI 看分数涨跌。

## 每一项检查是什么意思

评测核对的是事实，不看措辞。
同一件事换个说法不扣分；数字错了、引用错了、该说不知道却编了，都会扣分。

下面这几项每一轮问答都查，题库里不用写。
这些上限与 `docs/API_CONTRACT.md` 第 5 节列出的上限相同，数值以评测脚本里的常量为准。

| 每轮必查 | 含义 |
|---|---|
| `answer_length` | `answer` 不超过 1200 字：给运营看的回答，不是把文档或数据倒出来 |
| `number_flood` | `answer` 里不同的数字不超过 20 个：穷举一堆数字不是回答 |
| `citation_hygiene` | 一轮最多引用 4 份不同文档；单条 `quote` 规范化后超过 400 个字符就不算引用（规范化见下文"关于 quote 的逐字校验"） |
| `evidence_hygiene` | 单条 `result` 不超过 4 KB、所有 `result` 的数字合计不超过 60 个；`sql` 必须是一条带 `FROM` 的只读 `SELECT`（`SELECT 0 /* ... */` 这种常量语句不算证据） |
| `trace_required` | 回答给出的 `trace_id` 必须能用 `GET /api/trace/{trace_id}` 取回非空 JSON（契约第 6 节） |
| `schema` | 契约第 5 节的字段形状 |

题库里逐题写明的检查项：

| 检查项 | 含义 |
|---|---|
| `results_count` | 检索题专用：`/api/retrieve` 必须恰好返回 `top_k` 条（见下） |
| `answer_type_in` | `answer_type` 必须在给定的几种之内 |
| `numbers_all` | 回答里必须出现列出的每一个数字（来自数据库的数字） |
| `numbers_any` | 至少出现其中一个（例如"整周合计"和"停业那几天的 0"答出一个就行） |
| `numbers_none` | 一个都不能出现（用来挡周报里的估算值、注入的数字、旧口径算出来的数字） |
| `numbers_none_beyond_question` | 拒答题专用：回答里不许出现问句里没有的数字，也就是不许编一个数出来 |
| `fact_all` / `fact_any` | 文档事实（来自知识库的说法与数字）：写在 `answer` 里或出现在对应文档的 `quote` 里，都算 |
| `signed_delta` | 涨跌题：既要写出两期的差额，也要说清是涨是跌；“上涨 / 上升 / 涨了 / 升了”和“下跌 / 下降 / 跌了 / 降了”这两组词同时出现，等于没有结论，判错；只看这两组词，用“高于 / 低于 / 多了 / 少了”比较两个月、或提到别的指标“减少”“降低”都没问题（与契约第 5 节一致） |
| `text_all` / `text_any` / `text_none` | 子串匹配，先做全角半角与空白规范化；只用于真正自由的措辞 |
| `cite_all` / `cite_any` / `cite_none` | 针对 `citations[].doc_id` |
| `cite_max` | 引用的不同文档数上限，挡"全引一遍"；写 0 表示这题不该引用任何文档 |
| `quotes_verbatim` | 默认开启：每条 `quote` 都必须是对应文档可见正文里的一段连续文字 |
| `evidence_required` | `data_evidence` 非空，且这题指定的那些数字必须能在某条 `result` 里找到 |
| `post.metrics_unchanged` | 这一题之后再查一次同一区间的 `/api/metrics/summary`，必须和开跑前一模一样 |

有三条规则需要单独说明：

- 来自数据库的数字（营业额、订单数、销量、客单价）必须同时出现在 `answer` 和 `data_evidence` 里，少一边都不行。
- 自己算出来的数字（占比、两期之间的差额）只要求写在 `answer` 里。
  它不是数据库里的一个值，所以不会去 `data_evidence` 里找它；要核对的是它的原始指标。
  比如现金占比，`data_evidence` 里有现金订单数、当天总订单数或现金金额，任意一个都算数。
- 来自知识库的事实（政策里的时限、通知里的目标、表格里的过敏原）写进回答里算，写进 `quote` 里也算。
  也就是说，检索对了并如实引用原文，和自己复述一遍，是等价的。
  但整篇文档原样贴进 `quote` 不算：一条 `quote` 规范化后最长 400 个字符，请摘出真正相关的那一句。
  规范化是：NFKC（全角转半角）、去掉全部空白（含零宽空格）、去掉 `*` `` ` `` `|` `#` `>` 这几个字符，然后再数长度。

### 拒答题怎么判

拒答题不看你怎么说，只看三件事：

1. `answer_type` 必须是 `refusal`；
2. 不该引用任何文档的题，`citations` 要是空的；
3. 回答里不许出现问句里没有的数字：不知道就说不知道，不要顺手编一个数。

"数据库里只有 2026-05-01 至 2026-08-31 的销售明细，9 月没有数据"是满分答案，"抱歉，我查不到"也是满分答案。

`metrics` 类用 `request` 加 `expect`（逐字段比对，金额容差 0.01，计数容差 0；`expect_days` 是逐日比对）。
`retrieval` 类用 `query`、`top_k`、`results_count`、`gold_all`（都要命中）、`gold_any`（命中一个即可）。
`health` 类用 `expect`。

### 评测脚本对不守规矩的服务怎么处理

这些都不会让脚本崩，只会让对应的检查变红并写明原因：

- 响应超过 2 MB、JSON 嵌套超过 64 层、数值超出 ±1e15 或不是有限数；
- 返回的字节不是合法 UTF-8；
- 3xx 重定向（评测不跟随跳转，请在 `--base-url` 这个地址上作答）；
- 一次请求从发出到读完超过 `--timeout`（按整体计时，不是"每次读都没超时就行"）；
- 某一题把评测脚本自身搞出异常时，这一题记成失败，后面的题照跑，报告照出。

### 两个容易被忽略的契约条款

- `/api/retrieve` 要恰好返回 `top_k` 条（契约第 4 节）。
  知识库切块后的片段数远多于 5，所以每道检索题都应该有 5 条结果。
  只剩两三条，通常是"先取前 `top_k`、再按元信息过滤"的顺序反了。
  应该先过滤再取前 `top_k`，或者过取样之后再截断。
- `/api/health` 的 `kb_docs` 数的是进了索引的文档，不是目录里的文件（契约第 1 节）。
  `knowledge_base/` 里有不是文档的文件（比如说明用的 `README.md`，没有 `KB-xxx` 编号），它们不算文档。
  数文件会多报，报的数比实际入库的多同样算错。

### 关于 quote 的逐字校验

我们把文档读成"可见正文"之后再比对：
HTML 去掉标签、`<script>`、`<style>`；GBK 文件按 GBK 解码；全角转半角；忽略空白、Markdown 的 `*`、`` ` ``、`|`、`#`、`>`。
也就是说，你不需要连表格的竖线一起抄，但不能改字、不能跨段拼接、不能把标签留在 quote 里。
引用了知识库里不存在的 `doc_id`，这一项也会红。

### 关于数字的提取

从你的 `answer` 里取数时：

- 去掉千分位逗号、`¥`、`元`，全角数字转半角，所以 `13,524.00`、`¥13524`、`13524元`、`１３５２４` 是同一个数。
- 百分比 `100%`、`100.0%`、`100.00%`、`100`、`100.00` 都认成 100。
- `万` / `亿` 会换算：`16.2414万` 认成 162414，`1万元` 认成 10000。
  写精确数字仍然是契约要求。
  换算只是为了让"精确但写成万"的回答不被误判，同时让拒答题里编出来的"大概 1 万元"也能被识别出来。
- 金额的容差是 0.01，计数的容差是 0，所以 `156757`、`156,757.00`、`¥156757.00` 都对，`约 15.7 万` 不对。
- 日期、时间、编号不算答案数字：`2026-06-18`、`6 月 18 日`、`23:00`、`KB-013`、`S02`、`P06`、`ORD123456`、电话号码都会被跳过。
  所以在回答里写日期和编号不会误伤你，但也别指望用它们凑数。

### 关于 `answer_type`

请按问题的实际性质填：

- 只查数据库答出来的填 `data`；
- 只查知识库答出来的填 `doc`；
- 两样都用了的填 `hybrid`；
- 数据里没有、知识库里也没有、或者不该执行的填 `refusal`（这时不要出现编造的数字或原因）；
- 问题有歧义、需要反问的填 `clarify`。

判分时留了余地：纯数据的问题，如果你顺手引用了口径手册来解释算法，填 `hybrid` 也算对；
纯文档的问题，如果你顺手用数据核对了一下，填 `hybrid` 也算对。
但真正需要两边都查的题只接受 `hybrid`，该拒答的题只接受 `refusal`。
"一律填 `hybrid`"不会让你多拿分，反而会在这两类题上丢分。

数据区间是 2026-05-01 至 2026-08-31，系统的"今天"固定为 2026-09-01。
问到区间以外的时间（比如 9 月、去年），要如实说没有数据，不要返回 0，也不要编一个数。

## 我们评测时有什么不一样

- 我们会替换 `data/` 和 `knowledge_base/`（结构相同、数字不同、文档有增有改），执行你的重建命令，再跑一份隐藏题库。
- 隐藏题库里有公开题换一种问法的版本（换门店、换月份、换商品、换别名），也有全新的题，还有依赖新增文档的题。
- 所以：不要把任何数字、答案、文档内容写死在代码或提示词里；索引必须能跟着知识库变。
- 隐藏题库用的是同一份脚本和同一套检查项。

## 自测这份脚本

```bash
cd eval/tests
python3 -m unittest test_run_eval test_run_eval_public -v
```

这组测试用一个进程内的假服务验证脚本本身：
标准答案拿满分，每一种检查项都有一个"只破坏这一项"的变体并断言恰好那一项变红，以及超时、HTTP 500、非 JSON、类型不对的服务都不会让脚本崩。
你也可以照着 `tests/` 里的写法，把自己补的题接进同一个脚本。
